当前最佳优化栈：

```text
基础 FP32 fuse
+ MLP/GatedMLP input-grad fuse
+ line/atom attention CUDA fused op
+ directed2undirected CUDA fused op
```

P115 的关键优化点

P115 的核心不是普通“小 op 拼一起”，而是 compile 先发现了一个有效 backward 边界，然后落成手写 CUDA/C++ macro：

```text
LayerNorm backward
+ sigmoid / SiLU backward
+ gate/core multiply
+ second Linear input-grad
+ pre-second SiLU derivative
```

当前实现位置：

- Python 入口：`FusedInputGatedMLP._forward_after_first_projection`
- CUDA/C++ op：`matris_op.gated_tail_second_silu_input_grad_macro`
- 实现形态：CUDA tail backward + cuBLAS SGEMM + CUDA SiLU derivative epilogue
- 覆盖模块：
  - `attn_atom.edge_nonlinear_update`
  - `refine_atom.edge_nonlinear_update`
  - `attn_atom.node_nonlinear_update`
  - `attn_line.node_nonlinear_update`
  - 原 P113 覆盖的 line/refine GatedMLP second-tail 路径

当前 compile 结论

compile 的价值：用于发现“什么边界值得写 CUDA macro”。

目前最成功的 compile 边界：

```text
GatedMLP tail backward
+ second Linear input-grad
+ pre-second SiLU derivative
```

这个边界已经落成 P113/P114/P115 CUDA macro，并成为当前最佳。

不建议继续的 compile endpoint 路线：

1. refine_line 大边界 backward compile

- 需要启用 `refine_line` manual VJP wrapper。
- correctness：block0/block9 PASS。
- endpoint：
  - threshold=4096，无 warmup 排除：`87.750487 ms`
  - threshold=8192，排除前 20 warmup：`74.544084 ms`
- 结论：局部 microbench 很强，但 wrapper/cache/调度成本吃掉端到端收益；不采用。

2. 不走 P104、保留 CUDA op、外层 compile refine_line forward

- 开关：
  - `MATRIS_COMPILE_REFINE_LINE_FORWARD=1`
  - `MATRIS_COMPILE_REFINE_LINE_FORWARD_ROWS_THRESHOLD=0|8192`
- smoke20：
  - all rows：`78.737428 ms`
  - rows>=8192：`75.196740 ms`
- Dynamo 诊断：
  - `matris_op.PyCapsule.gated_tail_second_silu_input_grad_macro` 是黑盒。
  - `matris_op.PyCapsule.two_linear_silu_input_grad_backward_n128` 是黑盒。
  - 内部 `profile_prefix/module_name` 会触发 recompile limit。
- 结论：保留已有 CUDA op 后，compile 只能处理黑盒之间的小 glue，不适合作为 endpoint 优化。

后续如果继续 compile 辅助 fuse，应回到：

```text
局部 PyTorch baseline microbench
-> torch_eager / torch_compile / cuda_fused 三模式对照
-> 发现有效边界
-> 写 CUDA/C++/cuBLASLt/CUTLASS macro
-> 端到端 limit500 / limit5000 验证
```

不建议再直接把 compile 套在已有 CUDA fused 路径外层。

当前 no-go 摘要

这些方向已经筛过，除非后续 profile 给出新证据，否则不要直接重开。

1. 量化路线暂停

- W8A8/W4A8/fake quant/torchao/activation calibration sweep 不再作为当前主线。
- 当前最好结果都来自 FP32 fuse / CUDA macro。

2. Python manual VJP wrapper 不作为新主线

- attn_line 早期 P101 仍保留在最佳路径中，因为它对当前栈有效。
- refine_line R1/R2/R3 correctness 能过，但端到端不赢。
- 后续不要新增 wrapper 级 VJP；如要接管 backward，应做真正 C++/CUDA macro。

3. attn_line P108 后局部修补暂停

- grouped-alpha、split-edge、in-place-hidden、target-reduce、alpha-tiled 等方向 correctness PASS 但 endpoint 负收益。
- P108 dense op 内 SGEMM 已占主要时间；继续优化需要 cuBLASLt/CUTLASS epilogue/fused scatter 级实现。

4. refine_line/refine_atom 小分支暂停

- R-CUDA1/2/3/4 小分支或 wrapper 级 full macro 多次不赢。
- AT-CUDA1/P110/P111/P112 correctness 或 microbench 局部可行，但 endpoint 不赢。
- 后续只有在 P115 profile 显示 refine_line/refine_atom 重新成为 top hotspot 时再重开。

5. residual epilogue 暂停

- P116 full residual grad limit500：`76.133954 ms`
- P116 input-grad-only limit500：`75.909410 ms`
- 均慢于 P115 `73.482076 ms`。
- residual glue 太小，单独或简单并入 macro 都不值得继续。

下一步建议

优先级 1：profile 当前 P115 最佳路径

目标：

- 确认 P115 后新的 top hotspot。
- 重点看：
  - P113/P115 second-tail 内部 GEMM + SiLU epilogue 是否仍明显。
  - attn_atom 是否接近或超过 attn_line。
  - refine_line/refine_atom 是否重新成为主要热点。
  - scatter/gather/copy_layout 是否有新的集中长尾。

优先级 2：P113/P115 内部 GEMM/epilogue 优化

如果 profile 显示 P113/P115 内部仍是热点，考虑：

- cuBLASLt/CUTLASS epilogue：合并 `GEMM output * SiLU derivative`。
- grouped GEMM：减少多个 128x128 GEMM launch。
- 注意：不要自己手写普通 GEMM kernel 去替代 cuBLAS。

优先级 3：换新的 compile 边界找形态

只找尚未被 CUDA op 黑盒切断的 PyTorch baseline 局部边界。优先类似 P113 的长 elementwise/norm backward 链，不优先 scatter/reduce 小边界或 GEMM-heavy first projection。

继续盯 edge_alpha_project_scatter
这里包含 edge update input-grad、alpha projection input-grad、source/target scatter。它已经 fused 过，但还是最重。当前样本里有 rows 7064 / 5088 / 2086，其中 2086 还走 tile32，小图 tile32 仍然偏贵。下一步可以先做 threshold sweep，比如 4096 -> 2048 -> 1024，看更早切到 dense-GEMM 是否更好。

不优先重写 attention reduce backward 本体
fused_line_attention_backward_with_edge_direct_kernel 时间很小，继续优化它本体收益有限。更应该处理它前后的 contiguous/copy/index_add glue。

node_update backward 还有空间，但不能简单再包一层
它里面主要是 GatedMLP/GEMM/elementwise 链。P115 已经吃掉一部分，P116 residual 之前端到端失败，所以如果继续做，需要换成更大、更有针对性的 macro，而不是简单 residual add fuse。

copy/index_add/cat 是真实残余，但要并进大边界
单独写一个 copy 或 final_add kernel 不值得；它们应该并进 edge_alpha_project_scatter 或 node_update macro。
