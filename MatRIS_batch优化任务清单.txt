MatRIS sAlex Batch 推理 / 大 Batch 构图优化清单

更新时间：2026-05-31

本清单记录 MatRIS sAlex teacher `efsm` 路径上的 batch 调度、大 batch 推理和后续 NV batch 构图实验。它和 `MatRIS量化任务清单.txt` 分开维护：量化清单继续记录 P115 等单样本 endpoint 最佳主线；本清单只记录 batch 口径下的端到端效果、数值对齐和下一步构图优化。

核心口径

1. 最终性能仍只认端到端：
   `test/eval/infer_salex_lmdb_quant.py --measure-time`
2. 当前 batch 优化不是把单个晶体结构扩成更大的物理图，而是把多个独立结构拼成 batched disjoint graph。
3. 样本之间不互相连边；每个结构保持独立，只是在一次 `model.forward` 里合并处理。
4. 当前已完成的是：
   `逐样本 graph_converter + process_graphs batched graph + batched model forward`
5. 当前尚未完成的是：
   `NV true batch neighbor_list / batch graph construction`

当前结论

当前最优 batch 结果：

- 候选：P115 最佳 fuse 栈 + `batch_size=128` + `max_batch_atoms=2000`
- limit500 端到端总耗时：`10.608796 s`
- 吞吐：`47.130702 structures/s`
- 成功样本：`500/500`
- batch 数：`4`
- 最大 batch 原子数：`1350`
- 峰值显存：`54.456 GB`

相对 P115 单样本历史最佳：

- P115 batch=1 limit500：`36.741038 s`
- P115 batch=128 limit500：`10.608796 s`
- 端到端总耗时加速：约 `3.463x`

优化原因判断

sAlex 单样本通常很小，当前抽样 500 个样本合计约 `4948` 个原子，平均每个样本约 `9.896` 个原子。batch=1 时 GPU 看到的是大量小图，很多开销来自：

```text
Python / ASE / calculator 调度
CUDA kernel launch
GPU 同步
小 GEMM
小 scatter/gather
force/stress autograd 的小算子链
```

将多个独立结构拼成 batched graph 后，模型内部许多 GEMM 和 kernel 的有效输入变大，launch 和调度开销被摊薄。因此 batch 优化显著提升的是整体吞吐，而不是改变单个样本的物理图含义。

已实现改动

文件：`test/eval/infer_salex_lmdb_quant.py`

新增参数：

```bash
--max-batch-atoms
```

作用：

- `--batch-size` 控制单个 batch 最多包含多少个结构。
- `--max-batch-atoms` 控制单个 batch 最多包含多少个原子。
- 当原子数即将超过阈值时提前切 batch，避免显存风险。
- 默认值为 `0`，表示不启用原子数 cap；因此不影响原始 endpoint 口径。

```json
}
```

显存判断

当前 A800 80GB 上的观察：

- `batch_size=128, max_batch_atoms=2000`：峰值约 `54.456 GB`，推荐作为稳定 batch baseline。
- `batch_size=256, max_batch_atoms=3000`：默认 FP32 已到 `58.515 GB`，收益很小。
- `batch_size=500, max_batch_atoms=3000`：默认 FP32 已到 `66.982 GB`，收益几乎不变。
- 不建议直接跑不带 atom cap 的 full `batch_size=500`，因为 500 样本总原子数约 `4948`，E/F/S force/stress autograd 路径可能逼近或超过 80GB。

下一步计划

优先级 1：拆 batch 口径 stage profile

- 在 `P115 + batch_size=128` 口径下拆分：
  - graph_converter 总时间
  - process_graphs 总时间
  - model_forward 总时间
  - result export 总时间
- 目标：确认 batch 后构图占比是否明显上升。

优先级 2：接 NV true batch 构图

当前浅接 NV 只替换单样本 `structure.get_neighbor_list`，不推荐作为性能方向。真正要测试的是：

```text
多个 structure
-> 拼 positions/cell/pbc/batch_idx/batch_ptr
-> 一次 nvalchemiops.torch.neighbors.neighbor_list batch 调用
-> 生成 MatRIS batched graph
-> 直接进入 process_graphs / model forward
```

关键正确性要求：

- 不允许跨样本连边。
- atom edge set 与原 pymatgen 路径对齐。
- line graph 数量和映射需要验证。
- E/F/S 指标与 P115 batch=128 对齐。

优先级 3：避免 CPU 往返

如果 NV batch neighbor_list 本身有效，后续还需要减少 CPU 侧重组成本：

- tensor/CUDA 生成 directed2undirected。
- tensor/CUDA 生成 undirected2directed。
- tensor/CUDA 或高效向量化生成 line_graph。
- 最终目标是直接产出 MatRIS batched graph，减少 `Graph list -> process_graphs` 的 Python/CPU 开销。
