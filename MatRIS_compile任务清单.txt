MatRIS torch.compile 局部 fusion 实验清单

当前原则

- 不做 `torch.compile(model)` 全模型 compile。
- 只找已有手写 CUDA fused op 对应的原始 PyTorch baseline，然后做局部 `torch.compile(..., dynamic=True)`。
- 保留三种模式对照：
  - `torch_eager`：原始 PyTorch 等价实现。
  - `torch_compile`：同一 PyTorch 等价实现的局部 compile 版本。
  - `cuda_fused`：当前手写 CUDA fused op。
- 不删除、不改坏当前 CUDA fused op 路径；compile 实验只新增脚本和记录。
- 第一轮必须使用 `dynamic=True`，因为 AI4Science 输入的原子数、边数、line rows 会随样本变化。
- 如需检查 graph break / recompile，使用：

```bash
TORCH_LOGS="graph_breaks,recompiles" CUDA_VISIBLE_DEVICES=0 \
/home/lht/miniconda3/envs/matris311/bin/python test/eval/benchmark_local_compile_attention.py ...
```

第一目标：attention reduce 局部 fused op

对应关系：

| 模式 | 实现 |
| --- | --- |
| `torch_eager` | `Dimwise_softmax + alpha * attn_edge_feat + aggregate` 的等价 PyTorch 实现 |
| `torch_compile` | 上述 PyTorch 等价函数局部 `torch.compile(dynamic=True)` |
| `cuda_fused` | `matris_op.fused_line_attention_forward/backward` |

为什么先做这个：

- 这是已有 `line attention CUDA fused op` 和 `atom attention CUDA fused op` 共享的底层算子。
- 原始 PyTorch fallback 清楚：`Dimwise_softmax`、`source_alpha * value`、`target_alpha * value`、`aggregate(index_add/scatter_reduce)`。
- 可以用真实模型运行时捕获的 `source_logits/target_logits/values/source_index/target_index/num_segments` 离线比较三种模式，避免全模型 compile 的 graph break 干扰。

已新增脚本

- `test/eval/benchmark_local_compile_attention.py`
- `test/eval/benchmark_local_compile_attention_macro.py`
- `test/eval/benchmark_local_compile_directed_average.py`
- `test/eval/benchmark_local_compile_gated_tail.py`
- `test/eval/benchmark_local_compile_gated_tail_second_macro.py`

脚本行为：

- 运行真实 sAlex 样本，monkeypatch `interaction_block.fused_line_attention_or_none` 只用于记录实际进入 CUDA fused attention 的输入。
- 对同一批真实 attention case 离线比较：
  - forward time
  - forward+backward time
  - `max_abs_error / mean_abs_error`
  - rows、num_segments、line/atom case 类型
- warmup 会先触发 compile，统计阶段不包含第一次 compile 时间。
- 每次 timing 都使用 CUDA event 和 `torch.cuda.synchronize()`。

扩大边界实验：attention macro（2026-05-26）

边界：

```text
alpha_projection
+ attention_reduce
+ node_update_input_concat
```

三模式定义：

| 模式 | 实现 |
| --- | --- |
| `torch_eager` | PyTorch `edge_feat0 @ source/target_weight.T` + PyTorch segment attention reduce + `torch.cat([node, target, source])` |
| `torch_compile` | 上述 macro 的局部 `torch.compile(dynamic=True)` |
| `cuda_fused` | PyTorch alpha projection + `_CudaFusedLineAttention` + PyTorch cat |

结果文件：

- `results/compile_local_attention_macro_limit6_cases60_20260526.json`
- `results/compile_local_attention_macro_logs_smoke_20260526.log`

收集口径：

- 同样 60 个真实 attention case：30 个 atom，30 个 line。
- rows 范围：min `128`，mean `502.333333`，max `1520`。
- 日志 smoke 未发现 graph break / recompile。

forward：

| 模式 | weighted mean | 60 cases local total | 相对 eager |
| --- | ---: | ---: | ---: |
| `torch_eager` | `0.331886 ms` | `19.880346 ms` | `1.000x` |
| `torch_compile` | `0.314486 ms` | `18.819482 ms` | `1.055x` |
| `cuda_fused` | `0.146217 ms` | `8.669389 ms` | `2.270x` |

forward + backward：

| 模式 | weighted mean | 60 cases local total | 相对 eager |
| --- | ---: | ---: | ---: |
| `torch_eager` | `1.269414 ms` | `75.891917 ms` | `1.000x` |
| `torch_compile` | `0.751811 ms` | `44.805325 ms` | `1.688x` |
| `cuda_fused` | `0.401521 ms` | `23.870259 ms` | `3.162x` |

数值误差：

- `torch_compile` vs `torch_eager` 最大 forward abs error：`1.430511e-6`。
- `torch_compile` vs `torch_eager` 最大 backward abs error：`8.493662e-7`。
- `cuda_fused` vs `torch_eager` 最大 forward abs error：`1.430511e-6`。
- `cuda_fused` vs `torch_eager` 最大 backward abs error：`1.151115e-6`。

扩大边界判断：

- 相比只编 attention reduce，扩大到 `alpha_projection + attention_reduce + node_concat` 后，`torch_compile` 的 forward 收益从 `1.106x` 降到 `1.055x`，说明 Inductor 没能有效把 alpha matmul / cat 和 segment reduce 组合出更强融合。
- forward+backward 仍约 `1.688x`，和 attention reduce 单独 compile 的 `1.689x` 基本一致，说明收益主要仍来自 attention reduce/backward 本体，而不是新增的 macro glue。
- `cuda_fused` macro 对照从 attention reduce 单独的 `13.054x` forward+backward 降到 `3.162x`，原因是 macro 对照里 alpha projection 和 cat 仍是 PyTorch，CUDA fused 只覆盖中间 attention reduce；这说明扩大边界会稀释单个 fused op 的局部加速比。
- 当前结论：扩大到这个 macro 边界没有让 `torch_compile` 接近 CUDA fused 路线，暂时不支持继续盲目扩大到 full interaction block。

扩大边界实验：GatedMLP tail + second input-grad macro（2026-05-26）

边界：

```text
GatedMLP tail input-grad
+ core/gate second Linear input-grad
+ pre-second SiLU derivative
```

这个边界对应 GatedMLP backward 中从输出梯度往前的一段自然链：

```text
grad_out
-> tail backward 得到 grad_core_second_out / grad_gate_second_out
-> matmul(core_second_weight / gate_second_weight)
-> 乘 pre-second SiLU derivative
-> grad_core_first / grad_gate_first
```

三模式定义：

| 模式 | 实现 |
| --- | --- |
| `torch_eager` | 全 PyTorch macro：tail backward + 两个 matmul + 两个 SiLU derivative |
| `torch_compile` | 上述 macro 的局部 `torch.compile(dynamic=True)` |
| `cuda_tail_mixed` | CUDA tail backward + PyTorch matmul/SILU derivative |
| `cuda_tail_mixed_v2` | dim=128 时 CUDA tail v2 + PyTorch matmul/SILU derivative |

扩大边界判断：

- 这个结果支持“用 compile 扩大边界寻找 CUDA macro 形态”的思路。
- 单独 tail input-grad 时，CUDA fused tail 明显强于 compile；但扩大到 `tail + second input-grad + SiLU grad` 后，`torch_compile` 反而超过了“CUDA tail + PyTorch 周边 glue”的混合路径。
- 这说明当前 CUDA tail op 的边界偏小：tail kernel 本身快，但周围 matmul/SILU glue 留在 PyTorch 后，会吃掉一部分局部收益。
- 如果继续做自定义 CUDA 优化，方向不应是只微调 tail backward kernel，而应考虑更大的 backward macro：

```text
tail backward
+ second Linear input-grad GEMM
+ pre-second SiLU derivative
```

- 真正实现上不一定是一颗全手写 kernel。更实际的形态可能是：
  - CUDA tail backward 输出 grad_core/grad_gate；
  - cuBLAS/cuBLASLt 做两个 input-grad GEMM；
  - 用 fused epilogue 或后接轻量 CUDA kernel 合并 SiLU derivative；
  - 或者 CUTLASS epilogue 把 GEMM output 直接乘 SiLU derivative。
- 这条 compile 结果可以作为 CUDA macro 设计依据：边界扩大后有收益，且收益来自减少 tail 后的 PyTorch glue。

CUDA macro 反推验证：GatedMLP tail + second input-grad + SiLU epilogue（2026-05-26）

根据上一轮 compile 发现的有效边界，新增一个 feasibility CUDA macro：


- 如果只按 compile 自身收益看，最佳边界是 `GatedMLP tail input-grad`，约 `4.4x`。
- 扩到 `tail + second Linear input-grad + SiLU grad` 后，compile speedup 降到约 `3.4x`，但它覆盖了更多真实 glue，因此仍然是有价值的 fuse 形态发现。
- 再扩到 first projection 后，compile speedup 继续降到约 `3.1x`，且 rows 越大下降越明显；这个信号说明“继续扩大边界”对 compile 本身也没有变得更好。
- 因此后续用 compile 辅助 fuse 时，应该优先寻找类似 tail backward 的长 elementwise/norm 链，或中等边界的 glue macro；不要默认认为越大边界越好。

判断口径

- 如果 `torch_compile` 明显接近 `cuda_fused`，再考虑扩大 compile 边界到更大的纯 PyTorch attention/refine 子图。
- 如果 `torch_compile` 只接近 `torch_eager`，或者仍明显慢于 `cuda_fused`，说明当前手写 CUDA fused op 仍然值得保留。
- 如果 `TORCH_LOGS` 显示频繁 recompile，先记录触发原因；暂时不大改 dataloader。
- 只有当动态 compile 结果有希望但 recompile 明显拖累时，再考虑后续做 N/E/rows bucket + padding 的静态分桶 compile。

当前结论

- 对 attention reduce 这个局部子图，`torch.compile(dynamic=True)` 能带来一定 fusion 收益，但没有接近手写 CUDA fused op。
- 当前手写 CUDA fused attention op 应继续保留。
- 已尝试扩大到 `alpha_projection + attention_reduce + node_update_input_concat`，收益没有明显改善；不建议立刻扩大到全模型 compile。
- 已更换目标到 `directed2undirected average`，结果为 compile 负收益；该目标也不建议继续。
- 已更换目标到 `GatedMLP tail input-grad`，compile 明显正收益，是目前最值得作为 compile fusion 展示的局部目标；但 CUDA fused op 仍应保留。
- 已扩大 GatedMLP tail 边界到 `tail + second input-grad + SiLU grad`，compile 超过 CUDA-tail-only 混合路径，说明这块值得作为后续 CUDA macro 设计参考。
- 目前这组局部测试没有显示需要马上做 N/E bucket + padding；如果扩大 compile 边界后出现 shape guard/recompile，再考虑静态分桶。

下一步 compile 线建议

- 不建议继续在已有强手写 CUDA op 上做局部 compile 替代，因为 attention reduce 和 directed2undirected 两个代表目标都没有接近 CUDA。
- 如果还要继续 compile 线，优先围绕 GatedMLP tail macro 继续做真实路径验证：捕获或构造来自真实模块的 tail cache rows 分布，然后比较 `tail + second input-grad + SiLU grad` 是否能作为后续 CUDA/CUTLASS macro 的候选边界。
- 另一个方向是转向“尚未被自定义 CUDA op 覆盖、且 PyTorch glue 较多”的区域，例如普通 MLP/GatedMLP 非 fused fallback、refine/attention 里未替换的 cat/index_select/add/mul 小链路。
- 每个新目标仍按当前三模式口径记录：`torch_eager` / `torch_compile(dynamic=True)` / `cuda_fused 或现有最优路径`。

2. 优先排查是否还有未被 P113 覆盖的 GatedMLP tail-like backward，例如不同 dim、不同模块作用域、或周边 residual/add/mul glue。

- `MATRIS_COMPILE_REFINE_LINE_FORWARD=1`
- `MATRIS_COMPILE_REFINE_LINE_FORWARD_ROWS_THRESHOLD=0|8192`
- `MATRIS_COMPILE_REFINE_LINE_FORWARD_MODE=default`

实现：

- 在 `Interaction_Block.wrapper_refine_layer` 中对 line graph refine 调用加 env-gated compile 包装。
- 不启用 `MATRIS_P104_REFINE_LINE_R3_BLOCK_VJP`。
- 不关闭 P105/P106/P108/P113/P114/P115 等已有 CUDA op。

Dynamo 诊断：

- 自定义 CUDA op 被 Dynamo 视为黑盒：
  - `matris_op.PyCapsule.gated_tail_second_silu_input_grad_macro`
  - `matris_op.PyCapsule.two_linear_silu_input_grad_backward_n128`
- all-rows 版本触发 recompile limit，原因之一是：
  - `self.profile_prefix == 'interaction_block.7.refine_line'`
- 固定 `profile_prefix` 后，rows>=8192 版本仍在内部 GatedMLP 路径触发 recompile limit，原因之一是：
  - `self.module_name == 'interaction_block.7.refine_block_line_graph.edge_nonlinear_update'`

判断：

- 这条路线验证了之前的担心：当前已有 CUDA fused op 对 `torch.compile` 是黑盒，compile 只能处理黑盒之间剩余的小 glue。
- 直接“保留 CUDA op + 外层包 compile refine_line forward”不适合作为端到端优化方向。
- 不继续跑 limit500；当前最佳仍保持 P115。
- 如果后续还想用 compile，应该回到“局部 PyTorch baseline microbench 发现边界 -> 写 CUDA/CUTLASS macro”的模式，而不是在已有 CUDA fused 路径外层套 compile。
